# Deploy Skeleton on Cloudflare Workers Implementation Plan

## Overview

Move the scaffolded React Router v8 app from the Node template onto Cloudflare Workers, the platform chosen in `context/foundation/infrastructure.md`. Then deploy it automatically from GitHub Actions on every merge to `main`, gated on typecheck and build, and smoke-checked after deploy. This is roadmap foundation **F-01** (`deploy-skeleton`): it unlocks F-02 (game-room spike) and S-01 (access-key gate), and gives every later slice a deployed URL to verify against.

## Current State Analysis

- The app is the unmodified `create-react-router` v8.4.0 **Node** template.
  - Dependencies: `@react-router/node`, `@react-router/serve`, `react-router-serve` as the `start` script (`package.json:6-19`), plus a multi-stage `Dockerfile` and `.dockerignore`.
  - The UI is one index route rendering the template `Welcome` component (`app/routes.ts:3`, `app/routes/home.tsx`, `app/welcome/*`).
- `vite.config.ts:5-9` uses `tailwindcss()` + `reactRouter()` and Vite 8's native `resolve.tsconfigPaths`. It has no Cloudflare plugin.
- `tsconfig.json:9` sets `types: ["node", "vite/client"]`, and `include` already covers `**/*`, so a new `workers/` dir is picked up.
- `react-router.config.ts` sets `ssr: true` and has no `future` flags, which is correct for v8.
- Nothing exists yet for Cloudflare: no `wrangler.jsonc`, no `.github/`, no repo Actions secrets, no local wrangler install or login.
- The repo is private, its default branch is `main`, and local Node is v22.22.3 (React Router v8's minimum is 22.22.0).
- The user already has a Cloudflare account.

## Desired End State

- `npm run dev` runs the app inside the Workers runtime (workerd) through `@cloudflare/vite-plugin`.
- `npm run typecheck` and `npm run build` pass with Workers types generated by `wrangler types`.
- The app is live at `https://agent-werewolves.<subdomain>.workers.dev`:
  - `/` shows a minimal "Agent Werewolves" placeholder.
  - `/healthz` returns JSON with `status: "ok"`, the environment name, and the live Worker version ID, all read through the React Router v8 Cloudflare context.
- Every pull request runs typecheck, build, and a wrangler dry-run.
- Every push to `main` runs the same checks and only then deploys and smoke-tests `/healthz`. A failed smoke check turns the run red and prints the manual `wrangler rollback` procedure; it never rolls back automatically.
- No Node-server or Docker artifacts remain. The README documents dev, deploy, logs, secrets, and rollback.

Verify by merging a PR to `main` and watching `gh run watch` go green. Then confirm with `curl $PROD_URL/healthz` that the reported version ID matches the newest `wrangler deployments list` entry.

### Key Discoveries:

- **React Router v8 removed `AppLoadContext`.** `context` is always a `RouterContextProvider`, and `getLoadContext` / request-handler context must be a provider, not a plain object (react-router CHANGELOG v8.0.0, #15078; v8.0.1, #15207). Cloudflare's React Router guide and `cloudflare/templates/react-router-starter-template/workers/app.ts` still show the v7 pattern (`cloudflare: { env, ctx }` object + `AppLoadContext` augmentation), so do not copy them.
- **v8 removed the old dev proxy.** It dropped `@react-router/dev/vite/cloudflare` and all `future.v8_*` flags; the Vite Environment API is always on. Only `@cloudflare/vite-plugin` is needed, with no `future` config.
- **Package peers.** `@cloudflare/vite-plugin@1.64.0` peers on `vite ^6||^7||^8` and `wrangler ^4.151.0`. `@react-router/cloudflare@8.4.0` peers on `@cloudflare/workers-types@^4`, while `wrangler@4.151` peers on `^5`, so do not install `@react-router/cloudflare`.
- **`wrangler types`** (wrangler 4.x) writes `worker-configuration.d.ts` containing both `Env` bindings and runtime types for the configured compatibility date and flags. Add it to `compilerOptions.types` and keep `@types/node`, because `nodejs_compat` is on (developers.cloudflare.com/workers/languages/typescript).
- **The `version_metadata` binding** exposes `{ id, tag, timestamp }` of the running version (developers.cloudflare.com/workers/runtime-apis/bindings/version-metadata).
- SPA mode and prerendering are unsupported with the Cloudflare Vite plugin. This is fine because `ssr: true` stays.

## What We're NOT Doing

- No access-key gate (S-01), Durable Objects, Workflows, alarms (F-02), database, or Hyperdrive.
- No per-PR preview deployments. Only `main` deploys, and previews come with or after S-01.
- No automatic rollback in CI. Rollback stays a human action, per infrastructure.md's approval rules.
- No custom domain. The `*.workers.dev` URL is the production URL for now.
- No test framework (Vitest, workers pool). The smoke check on `/healthz` is the only runtime test in this change.
- No secrets beyond the two CI credentials. Runtime secrets arrive with the slices that need them.

## Implementation Approach

Work local-first. First make the app build and run in the Workers runtime on the developer machine (Phase 1), then give it something worth verifying (Phase 2). Then do one supervised manual deploy, which also sets up the account credentials (Phase 3). Only after that, automate the same commands in CI (Phase 4). Each phase ends in a state that typechecks and builds, so a stall leaves the repo usable.

## Critical Implementation Details

- **Avoid an import cycle with the context.** The typed Cloudflare context (`createContext<{ env: Env; ctx: ExecutionContext }>()`) must live in a module under `app/` that both the Worker entry and route loaders import. If it lives in `workers/app.ts`, routes would import the Worker entry, which itself dynamically imports the server build.
- **Build before you deploy.** `wrangler deploy` and `wrangler deploy --dry-run` must run *after* `react-router build`. The Vite plugin writes the deployable config into the build output and points wrangler at it. Running wrangler against the source `wrangler.jsonc` without a build deploys the wrong entry.
- **The deploy step needs `CLOUDFLARE_ACCOUNT_ID`.** Without it, a token scoped to one account still fails or prompts in non-interactive CI.

## Phase 1: Workers Runtime, Local

### Overview

Swap the Node runtime for the Workers toolchain so the existing app builds, typechecks, and runs locally inside workerd.

### Changes Required:

#### 1. Dependencies and scripts

**File**: `package.json`, `package-lock.json`

**Intent**: Remove the Node server runtime and add the Workers toolchain. Make typecheck regenerate Workers types so CI never depends on a committed generated file.

**Contract**:
- Remove `@react-router/node` and `@react-router/serve`.
- Add devDependencies `@cloudflare/vite-plugin` (^1.64.0) and `wrangler` (^4.151.0). Do NOT add `@react-router/cloudflare` or `@cloudflare/workers-types`.
- Scripts:
  - `dev`: unchanged (`react-router dev`, which runs in workerd through the plugin).
  - `build`: unchanged.
  - `cf-typegen`: `wrangler types && react-router typegen`.
  - `typecheck`: `npm run cf-typegen && tsc`.
  - `preview`: `react-router build && vite preview`.
  - `deploy`: `react-router build && wrangler deploy`.
  - `start`: removed.
- Add `"engines": { "node": ">=22.22.0" }`.

#### 2. Vite config

**File**: `vite.config.ts`

**Intent**: Run the SSR environment inside the Workers runtime in dev and build.

**Contract**: `cloudflare({ viteEnvironment: { name: "ssr" } })` from `@cloudflare/vite-plugin` is the **first** plugin, before `tailwindcss()` and `reactRouter()`. Keep `resolve.tsconfigPaths: true`. `react-router.config.ts` is unchanged.

#### 3. Wrangler config

**File**: `wrangler.jsonc` (new)

**Intent**: Declare the Worker, its runtime flags, observability, and the bindings `/healthz` reads.

**Contract**:
- `$schema`: `./node_modules/wrangler/config-schema.json`
- `name`: `agent-werewolves`
- `main`: `./workers/app.ts`
- `compatibility_date`: `2026-10-18`
- `compatibility_flags`: `["nodejs_compat"]`
- `observability`: `{ "enabled": true }`
- `version_metadata`: `{ "binding": "CF_VERSION_METADATA" }`
- `vars`: `{ "APP_ENV": "production" }`
- Local dev overrides `APP_ENV=development` through `.dev.vars`; document this but don't commit the file.

#### 4. Cloudflare context + Worker entry

**File**: `app/cloudflare-context.ts` (new), `workers/app.ts` (new)

**Intent**: Provide the v8-correct bridge from the Worker `fetch(request, env, ctx)` into React Router, so loaders read bindings with `context.get(cloudflareContext)`.

**Contract**: `app/cloudflare-context.ts` exports `cloudflareContext = createContext<{ env: Env; ctx: ExecutionContext }>()`. `workers/app.ts` default-exports `{ fetch }` `satisfies ExportedHandler<Env>`. For each request it builds a new `RouterContextProvider`, sets `cloudflareContext`, and calls the request handler with it:

```ts
const handler = createRequestHandler(
  () => import("virtual:react-router/server-build"),
  import.meta.env.MODE,
);

export default {
  fetch(request, env, ctx) {
    const context = new RouterContextProvider();
    context.set(cloudflareContext, { env, ctx });
    return handler(request, context);
  },
} satisfies ExportedHandler<Env>;
```

If `tsc` can't resolve `virtual:react-router/server-build`, add a minimal ambient module declaration next to the entry. Do not loosen `strict`.

#### 5. TypeScript config

**File**: `tsconfig.json`

**Intent**: Type the Worker against generated runtime and binding types.

**Contract**: `compilerOptions.types` becomes `["node", "vite/client", "./worker-configuration.d.ts"]`. Everything else is unchanged.

#### 6. Retire Node/Docker artifacts and ignore generated files

**File**: `Dockerfile`, `.dockerignore` (delete); `.gitignore`

**Intent**: Remove the deployment path the infra decision replaced, and keep generated or secret files out of git.

**Contract**: Delete both Docker files. Add `.wrangler/`, `.dev.vars*`, and `worker-configuration.d.ts` to `.gitignore`.

### Success Criteria:

#### Automated Verification:

- Clean install with no peer-dependency errors: `npm ci`
- No Node-server packages remain: `! grep -E '@react-router/(node|serve)' package.json`
- Types generate and typecheck passes: `npm run typecheck`
- Production build succeeds: `npm run build`
- Wrangler accepts the built Worker: `npx wrangler deploy --dry-run` (after build)

#### Manual Verification:

- `npm run dev` serves the existing page at `http://localhost:5173`, and the terminal shows it running through the Cloudflare plugin (workerd)
- Editing `app/routes/home.tsx` hot-reloads in the browser

## Phase 2: Placeholder Page + `/healthz`

### Overview

Replace the template UI with a project placeholder, and add a health route that proves SSR, static assets, and binding access through the v8 context.

### Changes Required:

#### 1. Placeholder home

**File**: `app/routes/home.tsx`; delete `app/welcome/` (3 files)

**Intent**: Show the project name instead of the React Router marketing page, so a deployed URL is recognisably this app.

**Contract**: `meta` title is "Agent Werewolves". The default component renders a minimal centered heading and a one-line description using Tailwind classes. It has no loader and imports nothing from `app/welcome/`.

#### 2. Health route

**File**: `app/routes/healthz.ts` (new); `app/routes.ts`

**Intent**: Give humans and CI one URL that confirms the Worker is serving, can read its bindings, and which version is live.

**Contract**:
- `routes.ts` registers `route("healthz", "routes/healthz.ts")` alongside the index route.
- The resource route's `loader` reads `env` from `context.get(cloudflareContext)` and returns `Response.json({ status: "ok", environment: env.APP_ENV, version: { id, tag, timestamp } })`, taking the version from `env.CF_VERSION_METADATA`.
- It sends the header `Cache-Control: no-store`.
- It has no default component, so it is a resource route.

### Success Criteria:

#### Automated Verification:

- Typecheck passes: `npm run typecheck`
- Build succeeds: `npm run build`
- Local Workers preview serves health JSON: start `npm run preview` in the background, then `curl -fsS http://localhost:4173/healthz | jq -e '.status == "ok" and (.environment | length > 0)'`
- Template welcome is gone: `! test -d app/welcome`

#### Manual Verification:

- `npm run dev` shows the "Agent Werewolves" placeholder at `/` with Tailwind styling applied
- `http://localhost:5173/healthz` returns JSON with `environment: "development"` when `.dev.vars` sets `APP_ENV=development`

## Phase 3: First Deploy + Account Wiring

### Overview

Do one supervised manual deploy from the developer machine, and create the credentials CI will need. Most steps need the human, because they involve the Cloudflare dashboard or account login.

### Changes Required:

#### 1. Cloudflare account preparation (human)

**File**: — (Cloudflare dashboard)

**Intent**: Make the existing account ready for API-driven deploys.

**Contract**:
- Confirm a `workers.dev` subdomain is registered (Workers & Pages → your subdomain).
- Create an API token from the "Edit Cloudflare Workers" template, scoped to this account only.
- Note the Account ID.

#### 2. First deploy (agent, after human login)

**File**: —

**Intent**: Prove the build deploys and serves before automating it.

**Contract**:
- Run `npx wrangler login` interactively (the human completes the browser step; on WSL, open the printed URL manually). Alternatively, export `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in the shell.
- Then run `npm run deploy`. Record the printed `https://agent-werewolves.<subdomain>.workers.dev` URL.

#### 3. Repo credentials for CI (agent)

**File**: — (GitHub repo settings via `gh`)

**Intent**: Store the CI deploy credentials and the production URL where the workflow reads them.

**Contract**:
- `gh secret set CLOUDFLARE_API_TOKEN`; the human pastes the token, and it never goes in chat or files.
- `gh secret set CLOUDFLARE_ACCOUNT_ID`
- `gh variable set PROD_URL --body "https://agent-werewolves.<subdomain>.workers.dev"`

### Success Criteria:

#### Automated Verification:

- Live health check passes: `curl -fsS "$PROD_URL/healthz" | jq -e '.status == "ok" and .environment == "production"'`
- Live version matches the latest deployment: the `.version.id` from `/healthz` equals the newest version ID in `npx wrangler deployments list`
- CI credentials exist: `gh secret list` shows `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, and `gh variable list` shows `PROD_URL`

#### Manual Verification:

- The production URL shows the placeholder page in a desktop browser
- `npx wrangler tail agent-werewolves --format pretty` prints a log line when `/healthz` is requested

## Phase 4: CI Deploy on Merge

### Overview

Automate Phase 3's deploy in GitHub Actions. Typecheck and build gate every PR and every push to `main`; pushes to `main` then deploy and smoke-test. Document the day-to-day operations in the README.

### Changes Required:

#### 1. CI workflow

**File**: `.github/workflows/ci.yml` (new)

**Intent**: One workflow, two jobs. PRs get fast feedback, and `main` deploys only on green checks.

**Contract**:
- Triggers: `pull_request` (any branch) and `push` to `main`.
- **Job `check`**: Node 22 with npm cache, then `npm ci` → `npm run typecheck` → `npm run build` → `npx wrangler deploy --dry-run`. It needs no secrets.
- **Job `deploy`**:
  - Runs only on `push` to `main`, `needs: check`, with `concurrency: { group: production-deploy, cancel-in-progress: false }`.
  - Steps: `npm ci` → `npm run deploy`, with env `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from secrets.
  - Then a smoke step: `curl` `${{ vars.PROD_URL }}/healthz` with retries (about 5 attempts, a few seconds apart), asserting `status == "ok"` with `jq`.
  - A final `if: failure()` step prints the rollback procedure: `npx wrangler deployments list`, then `npx wrangler rollback <previous-version-id>`, run by a human. It must not run the rollback itself.
- Permissions: `contents: read` only.

#### 2. README

**File**: `README.md`

**Intent**: Replace the template README with the operational facts an agent or human needs.

**Contract**: Sections:
- **Develop:** `npm run dev`, plus `.dev.vars` with `APP_ENV=development`.
- **Typecheck/build.**
- **Deploy:** automatic on merge to `main`; manual `npm run deploy`.
- **Health:** `/healthz`.
- **Logs:** `npx wrangler tail agent-werewolves`.
- **Rollback:** `wrangler deployments list` → `wrangler rollback <id>`, with the note that it needs a human.
- **CI secrets and variables:** names only.
- A link to `context/foundation/infrastructure.md`.

Remove the Docker and Node-server sections.

### Success Criteria:

#### Automated Verification:

- The workflow file is valid and runs on the PR for this change: `gh pr checks` shows `check` passing and `deploy` skipped
- After merge, the `main` run succeeds end to end: `gh run list --workflow ci.yml --branch main --limit 1 --json conclusion -q '.[0].conclusion'` returns `success`
- Production serves the merged version: `/healthz` `.version.id` equals the newest entry in `npx wrangler deployments list`

#### Manual Verification:

- Rollback drill: `npx wrangler rollback <previous-version-id>` succeeds, and `/healthz` then reports the previous version ID. Afterwards, re-deploy the latest (re-run the `main` workflow or `npm run deploy`) and confirm `/healthz` is back on the newest ID
- Review the README for accuracy against the actual commands

**Implementation Note**: After completing this phase and all automated verification passes, pause here for manual confirmation from the human that the manual testing was successful before proceeding to the next phase.

## Testing Strategy

### Unit Tests:

- None in this change; there is no logic beyond wiring. A test framework arrives with the first slice that has game logic.

### Integration Tests:

- `/healthz` acts as the runtime integration test, at three levels: locally against `vite preview` (Phase 2), against production by hand (Phase 3), and in CI after every deploy (Phase 4).

### Manual Testing Steps:

1. `npm run dev` → placeholder at `/`, JSON at `/healthz` with `environment: "development"`.
2. Merge a PR → `gh run watch` → green `check` and `deploy`, then `curl $PROD_URL/healthz`.
3. `npx wrangler tail agent-werewolves` while requesting `/healthz` → a log line appears.
4. Rollback drill as described in Phase 4.

## Performance Considerations

None at this stage. The placeholder and health route are trivial, well under the Free plan's 10 ms CPU limit per request.

## Migration Notes

None. There is no data and no prior deployment. The Docker/Node deployment path is removed, not migrated.
